# DR-0008: the M9 boot-policy profile

**Status:** proposed; the operator accepted its choices in discussion. Accepted when the M9-fit pull request merges.

## Context

M9 demonstrates software decisions on the emulated board: FIT signature checks, A/B slot selection, boot attempts, rollback, and recovery from damaged metadata and interrupted updates (spec §12, §17). It runs the whole chain from the QSPI flash (M8). Spec §12's limits apply: this proves a configured policy, not a hardware root of trust.

The vendor U-Boot (`renesas-u-boot-cip` `4eebfbaa4e`, `smarc-rzv2l_defconfig`) cannot run that policy as built (F, `tests/guests/out/fw/u-boot.config`):

| Needed | Effective configuration |
|---|---|
| FIT signature checks | `CONFIG_FIT=y`; `CONFIG_FIT_SIGNATURE` not set. `CONFIG_TOOLS_FIT_SIGNATURE=y` is the host `mkimage`, not the target. |
| an environment that survives a damaged copy | `CONFIG_ENV_IS_IN_MMC=y`, one copy at `0x1F0000`, 128 KiB; `CONFIG_SYS_REDUNDAND_ENVIRONMENT` not set |
| counters, slot selection, saving | `CONFIG_HUSH_PARSER`, `CMD_SETEXPR`, `CMD_ITEST`, `CMD_SAVEENV`, `CMD_EXT4`: present |

Spec §8 (REQ-GUEST-003) allows a firmware build-configuration change only for a closed hardware dependency. A boot-policy profile is a different purpose. The board's own product image (G2) enables the same kind of options: a redundant environment, FIT signatures and bootcount (`../evidence/EVK-2026-10-29-post-firmware.md`). G2 is studied as a sample only; nothing here builds from it or depends on it.

## Decision

1. **Two U-Boot profiles.** The vendor-default build stays as it is and keeps running M7's and M8's acceptance as the regression profile. A second build, the **M9 profile**, is the same pinned source with one listed configuration fragment and listed upstream source patches. The fragment, the patches and the build are in `tests/guests/fw/`, each with its reason. The fragment:
   - `CONFIG_FIT_SIGNATURE=y`, with the RSA and SHA-256 support it selects;
   - `CONFIG_SYS_REDUNDAND_ENVIRONMENT=y`, `CONFIG_ENV_OFFSET_REDUND=0x210000`;
   - `# CONFIG_LEGACY_IMAGE_FORMAT is not set`;
   - a built-in default environment that holds the M9 boot policy (decision 6), not the vendor's boot command.

   The one patch is upstream U-Boot `2092322b31cc`, a FIT-signature fix the pinned source predates (`tests/guests/fw/patches/u-boot-m9/`; M9-fit spec). Spec §8 gets a second exception for a project boot-policy profile, listed the same way (spec §22, v0.4).
2. **Media layout.** The two environment copies are at `0x1F0000`-`0x20FFFF` and `0x210000`-`0x22FFFF` on the module card. Partition 1 starts at `0x400000`. The image builder asserts these bounds. Partition 2 is slot A's root and partition 3 is slot B's. Each slot carries its own signed FIT in `/boot`, so a slot's kernel and root change together. The FIT holds the vendor kernel and the vendor DTB, unmodified (DTB-V, spec §8): it is not a consumer DTB.
3. **Trust anchor.** One RSA key per test profile, generated by the build the first time and kept with the untracked build outputs. Later builds and every negative case reuse that key. Each run records the SHA-256 of the public key, of U-Boot's control DTB that carries it, and of each FIT. The public key goes into U-Boot's control DTB with `required = "conf"`: U-Boot boots a configuration only if a signature by that key covers it.
4. **The boot route under test, and its bypass.** The automatic boot command loads the selected slot's FIT and runs `bootm` on its configuration. `booti` stays in the build, as the vendor has it. Acceptance proves enforcement along the configured automatic boot path only. It does not prove enforcement against someone who controls U-Boot's console, its environment or its firmware: such a person can run `booti` on any image, change the boot command, or replace U-Boot. Disabling legacy images does not close those routes. Spec §12 excludes that attacker. One stored variable could weaken the path itself: `bootm` checks signatures and hashes only while `verify` is not `n` (`boot/bootm.c:262`). The boot command therefore sets `verify` to `yes` at run time before `bootm`, and a refused case runs with `verify=n` stored. Linux writes the environment in M9-ab; a root user there can still rewrite the boot command, which stays outside §12's attacker model.
5. **Slot state.** The variables use RAUC's U-Boot names, so a RAUC profile could use the same state later: `BOOT_ORDER` (for example `A B`), `BOOT_A_LEFT`, `BOOT_B_LEFT`. M9 adds explicit update states:
   - `M9_PENDING=<slot>`: the updater wrote that slot and has not seen it boot healthily;
   - `M9_GOOD=<slot>`: the last slot that a health check committed.
6. **Boot attempts (U-Boot).** For each slot in `BOOT_ORDER`, in order, U-Boot takes the first slot whose counter is above 0. It then:
   1. decrements that counter and runs `saveenv`; if `saveenv` fails, it prints the slot and the failure and stops at the prompt, with no boot;
   2. loads the slot's FIT and runs `bootm` on it;
   3. if `bootm` returns (a rejected signature, a bad hash, a missing file), prints the slot and the reason, then resets the board. The attempt is already spent, so the next boot sees the lower counter.

   If no slot has an attempt left, U-Boot prints the slots it tried and every counter, and stops at the prompt. It does not replenish a counter, and it does not reset.
7. **Health and commit (Linux).** A boot service in each slot's root file system runs after start-up:
   1. It checks that `/` is the partition this slot should have, by PARTUUID, and that the slot's health checks pass.
   2. If they pass, it commits only the slot that is running: `BOOT_<slot>_LEFT=3` and `M9_GOOD=<slot>`. If `M9_PENDING` names this slot, it clears `M9_PENDING`: the update is committed.
   3. If `M9_PENDING` names another slot whose counter is 0, the service records the rollback (`M9_ROLLBACK=<slot>`), clears `M9_PENDING`, and puts the running slot first in `BOOT_ORDER`.
   4. If a check fails, the service changes nothing and reboots, so the slot's attempts run down.

   The service writes with `fw_setenv`, built from the same U-Boot source (`tools/env`), statically. It finds the card through the root partition's parent device at run time, so the name Linux gives the card (gap 22) does not matter.
8. **Update (Linux).** The updater writes the inactive slot's partition from a payload, checks the payload's SHA-256, then sets `M9_PENDING=<slot>`, that slot's counter to 3, and that slot first in `BOOT_ORDER`, in one `fw_setenv` call. The redundant environment writes the inactive copy and then switches to it. A reader therefore sees the whole old state or the whole new state, if the write of one copy is all-or-nothing (A, see decision 9).
9. **Damaged metadata.** U-Boot uses the valid copy with the higher serial number. If one copy is invalid, it uses the other one without a warning (`env_check_redund`, `env/common.c:447-493`), and the next save repairs it. If both copies are invalid, U-Boot prints its bad-CRC warning and uses the built-in default environment, and that default holds the M9 policy with `BOOT_ORDER=A B` and fresh counters. The fall-back is visible and still verified. It never falls back to the vendor's unsigned boot command.
10. **Interruptions.** A test stops the QEMU process at a declared point and starts a new QEMU on the same retained images: during the payload write, after the payload but before the selection is saved, and during the environment write. This tests the process-interruption boundary and the image files QEMU leaves behind. It is not evidence of real SD power-loss behaviour: QEMU hands guest writes to the host file, which is expected to finish them (I), while a card can tear a write. Finer fault injection needs its own declared semantics.
11. **Not in M9:** dm-verity, anti-rollback against an older validly signed image, RAUC itself, a network update, U-Boot writing the QSPI flash (the three-byte write remains unmodelled), eMMC boot partitions.

## Consequences

- REQ-GUEST-003 gets a second listed exception, and the device map's gap list names the M9 profile's fragment (REQ-GUEST-004).
- New requirements REQ-BOOT-001 to REQ-BOOT-00n (proposed in the unit specs), statuses set at release closure.
- The units: M9-fit (decisions 1-4), M9-ab (5-7, 9), M9-update-failure (8, 10).
- The vendor-default profile stays in every acceptance run, so M9 cannot hide a regression of M7 or M8.
